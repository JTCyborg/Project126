# Project 124 — сценарий расширения прошивки NeoGS до 48 КБ

**Ветка:** `main`  
**Каталог документа:** `NeoGS/`  
**Единственный файл прошивки на TR-DOS:** `neoprog.C`  
**Назначение документа:** фиксировать согласованную архитектуру, выполненные этапы, новые задачи, проверки и коммиты. Этот файл является контрольным планом работ и обновляется при каждом изменении реализации.

---

## 1. Цель

Увеличить объём прошивки NeoGS с текущего ограничения около 13 КБ до **48 КБ кода и данных**, сохранив существующий рабочий тракт загрузки, DMA и диагностики.

Файл `neoprog.C` остаётся **одним файлом**. Bootstrap остаётся **встроенным в начало этого файла**. Spectrum не обязан хранить весь файл в памяти одновременно: файл читается с TR-DOS последовательно порциями через один повторно используемый буфер размером не более доступных 16 КБ. Общий размер файла не ограничен размером буфера.

## 2. Зафиксированные требования — не менять без прямого согласования

1. Ветка GitHub: `main`; рабочая папка проекта: `NeoGS/`.
2. На диске TR-DOS используется один файл `neoprog.C`.
3. В начале `neoprog.C` находится встроенный bootstrap. Отдельный bootstrap-файл для пользователя и отдельный runtime-файл на диске не вводить.
4. Загрузка с TR-DOS выполняется последовательно: очередная порция читается в буфер, передаётся в NeoGS, буфер используется повторно для следующей порции. Буфер — не более 16 КБ; общий файл может быть больше 16 КБ, в том числе до требуемых 48 КБ прошивки плюс bootstrap и заголовки.
5. Целевая карта логического адресного пространства NeoGS:

   | Диапазон | Размер | Назначение |
   |---|---:|---|
   | `#0000–#3FFF` | 16 КБ | Основная прошивка и рабочие данные |
   | `#4000–#4FFF` | 4 КБ | Дополнительный код прошивки / служебный переход |
   | `#5000–#7FFF` | 12 КБ | Существующее DMA-окно x86 — не изменять |
   | `#8000–#BFFF` | 16 КБ | Дополнительный код и данные прошивки |
   | `#C000–#EFFF` | 12 КБ | Дополнительный код и данные прошивки |
   | `#F000–#FFFF` | 4 КБ | Стек Z80 и резерв |

6. Сохранить проверенную DMA-конфигурацию:
   - физический адрес DMA: `#00D000`;
   - логическое окно x86: `#5000–#7FFF`;
   - заголовок: `#5000`;
   - старт x86 payload: `#5002`;
   - максимальный payload текущего DMA-окна: `#2FFE`;
   - значение PG1 по проверенной конфигурации: `#03`.
7. Сохранить отладочный вывод через порт `#EF` и существующий тракт GSDAT/DBIT → host debug port.
8. Не смешивать прошивку Z80 NeoGS (`neoprog.C`) и отдельный x86 payload (`x86task.C`).
9. Не менять проверенные тесты, адреса DMA и загрузочный handshake без технической необходимости и отдельной фиксации причины.
10. Не добавлять несогласованные задачи, новые файлы загрузки или изменения других подсистем проекта.

## 3. Текущее состояние исходников (зафиксировано при создании документа)

### 3.1. Host-side загрузчик

Файл: `zx_main/neogs_driver.asm`.

На момент создания документа:
- `load_neogs_firmware_file` получает длину файла из дескриптора TR-DOS;
- проверяет размер как максимум `#4000` (16 КБ);
- читает сектора последовательно, но размещает их по возрастающим адресам начиная с `#C000`;
- тем самым фактически пытается держать весь пакет в одном 16-КБ диапазоне;
- `upload_firmware` получает указатель на целый пакет в памяти хоста и передаёт сначала bootstrap, затем firmware;
- текущая проверка длины прошивки ограничивает её значением `#3400`.

Это существующие ограничения реализации, а не ограничения TR-DOS или протокола передачи. Их необходимо устранить потоковой передачей через повторно используемый буфер.

### 3.2. Сборка прошивки

Файл: `neogs_sub/build_firmware.asm`.

На момент создания документа:
- `neogs_firmware_end <= #3400`;
- прошивка сохраняется как непрерывный `neogs_code.bin`;
- bootstrap собирается отдельно как промежуточный артефакт;
- пакет формируется build-скриптом из bootstrap и firmware.

Текущая сборка ограничивает прошивку диапазоном ниже `#3400`. Сборку требуется переделать под сегменты целевой карты, сохранив один итоговый пакет `neoprog.C` для TR-DOS.

### 3.3. NeoGS memory mapping

В `NeoGS/` находятся Programmer's Guide, `ports.inc` и исходники модели NeoGS в Unreal Speccy. Для отображения окон используются механизмы `GSCFG0`, `MPAG` и `MPAGEX`. Выбор физических страниц и порядок переключения должны быть сверены с Programmer's Guide и реализацией эмулятора до внесения кода, который зависит от этих значений.

DMA-регистры Spectrum-side и внутреннее отображение памяти Z80 NeoGS — разные механизмы. Их нельзя смешивать.

## 4. Подтверждённая рабочая база

По последнему пользовательскому логу успешно проходили:
- bootstrap и ready-handshake NeoGS;
- CBIT/DBIT и DMA;
- x86 HLT, AX=`#BBAB`;
- пять диагностических edge cases интерпретатора;
- 64 страницы x86 RAM, word/segment wrap;
- BIOS IVT/BDA и 640 KiB;
- interrupt stack frame, IRET и guest INT 20h;
- базовые группы инструкций MOV, INC/DEC, арифметика, логика, ModR/M, segment override, LOOP/JCXZ/JMP/Jcc, PUSH/POP;
- BIOS INT 10h и 42-column console;
- Stage 5 TR-DOS task-file load и DMA;
- итоговый статус `AX=#BBAB`.

Это результат пользовательского запуска, а не заявление о повторной проверке в текущей сессии.

Последние известные коммиты проверенной базы:
- `503d1129ae6f883906890bfff6031e17be0600ca` — документирование проверенной DMA-карты;
- `03a928713f13b8d500d2bced93ce225bcfbed72d` — корректировка ожидаемого AX для неизвестного opcode.

## 6. Правила ведения работ

1. Перед каждой правкой перечитать актуальный файл из `main` и использовать актуальный SHA.
2. До изменения кода свериться с этим сценарием. Любая новая задача сначала записывается в раздел 5 или 7.
3. Не выполнять работы, не относящиеся к цели 48-КБ прошивки и необходимым для неё зависимостям.
4. После каждого законченного этапа обновлять этот файл: отмечать выполненное, добавлять новые обнаруженные пункты, записывать изменённые файлы, commit SHA и статус проверки.
5. Не отмечать пункт выполненным только потому, что код написан или закоммичен. Для статуса PASS требуется фактическая сборка/проверка; пользовательские проверки помечать как «PASS по логу пользователя».
6. Не менять утверждённые адреса, размер/назначение DMA-окна, имя единственного файла или архитектуру «один файл + встроенный bootstrap» без прямого указания пользователя.
7. Не заявлять о сборке, запуске или аппаратной проверке, если соответствующая проверка не выполнялась.
8. Если обнаружена проблема вне текущего объёма, записать её в «Отложенные замечания» и не переключать на неё работу без необходимости.

### 2026-11-02 — V2 Stage0 DBIT wait policy

- **Изменён:** `neogs_sub/bootstrap_v2_stage0.asm`.
- **Наблюдение по runtime:** последний лог после host turnaround delay всё ещё останавливается на отправке `#12`: `LAST RX BYTE=#A1`, `LAST TX BYTE=#12`, `TX WAIT STATE=2`, `GSSTAT=#FE`. Следовательно, задержка host-side `#0400` не устранила зависание.
- **Проверено по эмулятору:** `NeoGS/gsz80.cpp` вызывает `flush_gs_z80()` перед host-side чтением/записью портов; `in_gs(#B3)` очищает DBIT только после flush. Сам `flush_gs_z80()` исполняет Z80 только до временной границы, рассчитанной по текущему времени host CPU (`NeoGS/gsz80.inl`), а не безусловно целый кадр. Поэтому утверждать, что один вызов flush гарантированно исчерпывает `#FFFF`-тайм-аут Stage0, нельзя.
- **Изменение:** удалены независимые instruction-count тайм-ауты Stage0 из приёма байта и ожидания потребления исходящего байта. Stage0 теперь ждёт DBIT без собственного таймера; конечный тайм-аут и диагностика остаются на host стороне. Это исключает рассинхронизацию двух независимых счётчиков времени как причину локального перехода Stage0 в halt. Проверка длины Stage1 и явный error ACK сохранены.
- **Ограничение вывода:** это устранение потенциального ложного локального timeout, а не доказанное исправление причины отсутствия DBIT-clear на `#12`. Следующий runtime log должен показать, прошёл ли обмен длиной и дошёл ли host до `#A3`.
- **Коммит кода:** `0a04c107ca63c24beba84c037aa5a07a6eb7c13c`.
- **Проверка:** GitHub commit создан в `main`; assembler/CI и runtime для этого изменения ещё не подтверждены. Не считать V2 runtime PASS.


### 2026-11-02 — runtime log: Stage0 does not acknowledge first length byte

- **Получен runtime log пользователя:** package length `#4123`, sectors `#0042`; `DATA BYTES SENT=#007A`; `BOOT PHASE=#0010`; `LAST RX BYTE=#00A1`; `LAST TX BYTE=#0002`; `TX WAIT STATE=#0002`; `LAST GSSTAT=#00FE`; buffer remaining `#0083`, next TR-DOS sector `08:07`.
- **Интерпретация:** Stage0 отправил READY `#A1`; host затем выставил DBIT с байтом `#02` и ожидает его чтения. DBIT остаётся установленным, поэтому host не засчитывает этот байт. По host code `gs_boot_send_data_byte` счётчик `DATA BYTES SENT` увеличивается только после DBIT-clear. Таким образом, `#02` не подтверждён как принятый.
- **Сопоставлено с моделью Unreal Speccy:** ZX-side `GSDAT=#B3` write устанавливает DBIT; GS-side `ZXSTAT=#04` читает состояние; GS-side `ZXDATRD=#02` возвращает `gsdata_out` и очищает DBIT. Определения находятся в `NeoGS/ports.inc`, реализация — в `NeoGS/gsz80.cpp`.
- **Важное ограничение:** лог доказывает отсутствие DBIT-clear после host write, но не показывает PC/состояние GS Z80. Пока нельзя заключить, завис ли Stage0 в receive loop, остановился ли CPU scheduler или исполнение ушло по иному пути. Удаление локальных Stage0 timeout не исправило runtime.
- **Изменения кода:** не вносились. Не добавлять новые задержки/переходы без диагностики причины.
- **Проверка:** GitHub Actions для коммитов `0a04c107ca63c24beba84c037aa5a07a6eb7c13c` и `2dce9a30020f16aae448035606d5b3363ece9649` завершились `success` (build/assembler CI PASS). Runtime V2 остаётся FAIL по приведённому логу.
- **Следующий шаг:** проверить GS Z80 execution/synchronization на участке после чтения host READY `#A1`: установить, доходит ли PC до цикла `v20_receive_byte` и выполняется ли `in (#02)` после установки DBIT. До получения такого доказательства не менять handshake.
